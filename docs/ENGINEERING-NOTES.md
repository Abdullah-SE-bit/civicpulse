# Engineering Notes

Answers to the eight questions in assignment §5.2, with file-and-line references. Filled in as the implementation lands; unanswered sections are marked TODO rather than guessed. Line numbers are for the commit this file was last edited on.

1. **Laptop vs CI runner.** Three real differences and what freezes each. (a) *OS and runtime versions.* The laptop that wrote most of this is Windows 11 with Node 24 and Python 3.14; the runner is Ubuntu 24.04 with Node 22 and Python 3.12 (`actions/setup-node`/`setup-python`, `.github/workflows/ci.yml:49,58`). Inside images the versions are frozen in `backend/Dockerfile:1,8` (`python:3.12.14-slim-bookworm`) and `frontend/Dockerfile:10` (`nginxinc/nginx-unprivileged:1.27.5-alpine`). Both final stages also run `apt-get upgrade` / `apk upgrade`, added after Trivy reported 44 and 38 HIGH/CRITICAL findings in the older pinned bases (CI run 36048931292); that trades a little reproducibility for security fixes, and Trivy in CI is what catches drift. Gap: `frontend/Dockerfile:2` pins only `node:22-alpine`, a moving tag, and CI's non-image jobs pin only the major version. (b) *Dependency versions.* Frozen for the frontend by `package-lock.json` plus `npm ci` (`frontend/Dockerfile:5`). **Not frozen for the backend**: `backend/pyproject.toml` uses `>=` ranges and `backend/Dockerfile:6` installs whatever is newest, so a laptop and a runner can resolve different versions. (c) *Configuration and services.* A laptop has a real `.env` and possibly a real LLM key; CI has neither: `TRIAGE_PROVIDER: simulated` is set for the whole workflow (`ci.yml:17`) and the integration job builds its `.env` from the committed placeholders (`ci.yml:146`). Line endings are a fourth we hit: Git on the laptop warns "LF will be replaced by CRLF" on every file, so anything shell-run in a Linux container (`scripts/integration.sh`, `backend/entrypoint.sh`) depends on the repository blob being LF.
2. **CI/CD maturity.** The lecture's ladder is not in this repository, so I do not name a rung from it; here is what the pipeline actually does. CI runs lint, type-check, tests, image build with a Trivy scan, kustomize|kubeconform, and a Compose integration test on every PR to `main` and push to `dev` (`ci.yml`). CD on push to `main` runs the tests again, publishes SHA-tagged images and an SBOM, and deploys the prod overlay to an ephemeral kind cluster with a smoke test (`cd.yml`). There is no long-lived environment, no manual approval gate, no image signing and no automated rollback. The next step, and what it buys: deploy by digest with Cosign verification (a tag can be overwritten, a digest cannot; ADR 0003), then a persistent staging cluster so the deployment is exercised over time rather than only at creation. `cd.yml` has run once on `main` (`docs/evidence/cd-run.md`, run 36102402634) and passed; `release.yml` has not run.
3. **Build once, deploy many.** Two lines carry it. The image is built once in `build-push` (`.github/workflows/cd.yml:39-71`) and the deploy job references that same commit-SHA tag (`cd.yml:135`, `kustomize edit set image ...:$SHA`), so what was tested is what runs. And the frontend contains no environment-specific value: it calls same-origin `/api`, which nginx forwards to `backend:8000` (`frontend/nginx.conf:8`; ADR 0002). All environment-specific values enter at runtime through the ConfigMap/Secret (`k8s/base/configmap.yaml`) or Compose `${...}` variables. Without the nginx line, the API URL would be baked into the bundle at build time and the frontend would need a rebuild per environment, so the tested artifact would not be the deployed one. What has been shown: the images CI builds run in Compose and in a kind cluster with only environment differing (`docs/evidence/compose-run.md`, `docs/evidence/k8s-run.md`). CD then did exactly this with the published images: `cd.yml` pushed SHA-tagged images to GHCR and deployed those same tags to a kind cluster (`docs/evidence/cd-run.md`). The Compose and kind evidence runs used locally built `:dev` images.
4. **What "correct" means for a probabilistic LLM component, and how CI stays deterministic.** With a live model the same complaint can get different output, so "correct" cannot mean "same label as last time". For the triage component it means four checkable properties, none of which depend on the model being right: (a) whatever comes back is a valid `TriageResult`: enum category and priority, summary <= 140 chars, confidence in [0, 1] (`parse_triage_json`, `backend/app/providers/triage/base.py:56`); anything else is rejected, not repaired; (b) a request never fails because the model did: any provider error becomes `rules:fallback` (`backend/app/services/triage_service.py:78-91`); (c) latency is bounded per call (`TIMEOUT_SECONDS = 10.0`, `providers/triage/llm.py:12`) with at most one retry, only for timeout/429/5xx (`triage_service.py:96-102`, `llm.py:15-19`); (d) complaint text cannot steer the schema (delimited as data, `base.py:51`, and the output is validated regardless). Whether the label is *accurate* is a separate, unmeasured question: there is no labelled evaluation set in this repository, so we make no accuracy claim. CI stays deterministic by construction: it runs `TRIAGE_PROVIDER=simulated` (hash-derived output, `providers/triage/simulated.py`), and the LLM/Ollama providers are tested through `httpx.MockTransport`, so no test touches a network or sleeps (the retry sleep is injected, `TriageService(sleep=...)`). Tests: `backend/tests/test_triage.py`, `test_api.py::test_provider_that_always_raises_still_returns_201_with_rules_fallback`.
5. **HPA lag (measured, with caveats).** On a kind cluster inside a shared 4-vCPU GitHub runner (k6 on the same host), k6 offering 120 req/s to `GET /api/complaints?page_size=100` (`load/k6-script.js`): the HPA first wanted more than 2 replicas **27 s** after the load arrived (run 1; 33 s in run 2), the Deployment was scaled at the same moment, the first new pod was Ready **36 s** after (42 s), and the HPA's own status caught up at 42 s (48 s). Resolution is about 2 s. Where the time went: 27-33 s passed *before* any decision (the ramp itself, the metrics-server scrape and the HPA's sync loop), then about 9 s from decision to first Ready pod (scheduling, the `migrate` init container, startup probe), then a second step to reach 10 pods because the scale-up policy adds at most +4 pods or +100% per 15 s (`2 -> 4 -> 8 -> 10`). At 10 pods CPU still sat at 72-75% of request, above the 60% target, i.e. `maxReplicas` and the 100m request were the binding limit, not the autoscaler's speed. What would reduce the lag is untested: a shorter metrics resolution, a higher `minReplicas`, skipping migrations in scale-out pods. Data, chart and `kubectl get hpa -w` capture: `docs/evidence/k8s-run.md`, `docs/evidence/k8s/`. Repeated across three runs on fresh runners (decision 27-34 s, first Ready pod 36-43 s): consistent in order of magnitude, but shared hardware, so treat the numbers as indicative.
6. Why VPA is in Off mode: HPA on CPU and VPA in Auto mode both act on the CPU request and fight (VPA raises the request, utilisation drops, HPA scales in, per-pod load rises, VPA raises again). VPA runs recommender-only; we read `kubectl describe vpa backend-vpa` and change requests ourselves. (k8s/optional/vpa.yaml) We saw the mechanism happen once: after run 1 the recommender's CPU target was 163m; applying it (request 100m -> 163m) lowered the HPA's reported utilisation for the same work, and the same load then needed 9 replicas at about 50% CPU instead of 10 at 72-75% (`docs/evidence/k8s-run.md`). In `Auto` mode VPA would make that change itself, repeatedly, while the HPA reacts to it. The recommendation itself was not stable (93m in an earlier run of the same setup) and its upper bound (about 40 cores) was meaningless with only minutes of history, which is a second reason to have a human decide.
7. `internal: true` network vs a hosted LLM call: the backend is the only service on both networks, so it keeps a route out via `edge` and calls the hosted LLM itself. Postgres and Redis stay internal-only. The alternative (a dedicated egress proxy service on both networks) adds a moving part with no gain here. Ollama sits on `edge` because it must download model weights. (compose.yaml) Trade-off worth knowing: the backend is now the one service that has both internet egress and access to the data. The Kubernetes manifests contain no NetworkPolicy, so the cluster deployment does **not** have an equivalent of this isolation.
8. **The failure that cost more than an hour.** Not measured in wall-clock time, so we make no duration claim; it is the failure that cost the most rework. Symptom: a backend commit, its Issue and its PR all appeared under the *other* teammate's GitHub account. We first assumed each Claude session kept its own identity. The truth came from `git log --all --format='%h %an <%ae>'` (the commit was authored `rayyanhasan899`) and `gh auth status` (active account `rayyanhasan899`), plus `git config --show-origin --get user.email`, which printed `.../CivicPulse/.git/config`: both sessions shared one machine, so the `gh` active account is global and the repo-local git identity is shared by every worktree. Fix: closed the wrong PR and issue, amended the one commit with `git commit --amend --reset-author` and pushed with `--force-with-lease` to that unmerged branch, then set the identity per command via `GH_TOKEN="$(gh auth token --user Abdullah-SE-bit)"` and `GIT_AUTHOR_*`/`GIT_COMMITTER_*`, verified with `gh api user --jq .login` before every write. Lesson: identity is process state, not session state; verify it before each write, not once at the start.

## Index justifications
Both are created in `backend/alembic/versions/0001_create_complaints.py:45,47`. I have **not** run `EXPLAIN` against PostgreSQL (none available on the machine that wrote this), and at 32 seed rows the planner would pick a sequential scan anyway, so these are design justifications, not measured speedups.
- `ix_complaints_status_priority (status, priority)`: the dashboard filter `SELECT ... FROM complaints WHERE status = ? AND priority = ? ORDER BY created_at DESC LIMIT ? OFFSET ?` and its `count(*)` (`ComplaintRepository.search`, `backend/app/repositories/complaints.py:42`). The leading column also serves status-only filters. It does **not** serve category filters, and it is not a fit for `/api/stats` (`GROUP BY category` / `GROUP BY priority`, `count_by`, line 65); those aggregate the whole table by design and are cached in Redis instead.
- `ix_complaints_created_at (created_at)`: the unfiltered dashboard page `ORDER BY created_at DESC LIMIT ? OFFSET ?` (`search`, line 54) and `/api/meta/providers` `ORDER BY created_at DESC LIMIT 20` (`recent_triage`, line 73). With a status/priority filter the planner may prefer the composite index and sort instead; that is expected.

## Redis on a volume (AOF)
Redis here does three jobs: the `/api/stats` read-through cache (30 s), the distributed rate limiter (60 s windows), and the 24 h triage-result cache. The first two lose almost nothing on restart: a stats entry is recomputed on the next read and a limiter window is gone within a minute anyway. The third is the reason for the volume: cached triage results are what keep duplicate complaints (a burst main reported by nine neighbours) from re-spending a rate-limited free LLM quota, and a restart with no persistence would discard up to a day of them. AOF on `redisdata` (`compose.yaml`, `--appendonly yes`) keeps them across `docker compose down`/`up`. This is a judgement call, not a correctness requirement: nothing breaks if the volume is lost, and we have not measured the hit rate or AOF overhead. (compose.yaml)
